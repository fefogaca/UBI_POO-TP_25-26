\section*{Resumo}
\addcontentsline{toc}{section}{Resumo}

Este relatório documenta a evolução de um sistema de gestão de farmácia desenvolvido no âmbito da disciplina de Programação Orientada a Objetos. A segunda entrega introduziu uma interface gráfica baseada em Java Swing, persistência de dados através de serialização de objetos, testes unitários JUnit 5 e documentação com JavaDoc. O código foi reorganizado em pacotes (\texttt{app}, \texttt{modelo}, \texttt{gui}, \texttt{persistencia}, \texttt{test}) e beneficiou de refatoração orientada por princípios de POO, resultando numa aplicação mais robusta, reutilizável e preparada para futuras extensões.

\section*{Palavras-chave e \textit{Keywords}}
Java; Swing; GUI; Programação Orientada a Objetos; Persistência de Dados; Serialização; JUnit; Javadoc.

\begin{verbatim}
javac -cp "lib/junit-platform-console-standalone-1.10.2.jar:src" -d out \
  $(find src -name "*.java" ! -path "*/test/*")
\end{verbatim}
    Alternativamente, sem utilizar \texttt{find}:
\begin{verbatim}
javac -cp "lib/junit-platform-console-standalone-1.10.2.jar:src" -d out \
  src/app/*.java src/modelo/*.java src/gui/*.java src/persistencia/*.java
\end{verbatim}
    \item Compilar classes de teste:
\begin{verbatim}
javac -cp "lib/junit-platform-console-standalone-1.10.2.jar:out" -d out \
  $(find src/test -name "*.java")
\end{verbatim}
    \item Executar a aplicação GUI:
\begin{verbatim}
java -cp "out" app.Main
\end{verbatim}
\end{enumerate}

\subsection{Execução de Testes Unitários}

\section{Estrutura da Solução Construída}

\subsection{Visão Geral}
O código encontra-se organizado por responsabilidade:
\begin{itemize}
    \item \textbf{Pacote \texttt{app}}: ponto de entrada \texttt{Main}.
    \item \textbf{Pacote \texttt{modelo}}: domínio da aplicação (entidades e regras).
    \item \textbf{Pacote \texttt{gui}}: interface Swing (janela principal e painéis).
    \item \textbf{Pacote \texttt{persistencia}}: gestão de ficheiros para serialização.
    \item \textbf{Pacote \texttt{test}}: testes JUnit 5.
\end{itemize}

\subsection{Detalhamento dos Ficheiros}
\begin{itemize}[leftmargin=15pt]
    \item \textbf{\texttt{src/app/Main.java}}: Carrega dados, inicializa \texttt{Farmacia} e arranca a GUI. Lança a aplicação na Event Dispatch Thread.
    \item \textbf{\texttt{src/modelo/Pessoa.java}}: Classe abstrata base com nome e NIF. Obriga subclasses a implementar \texttt{toString()}.
    \item \textbf{\texttt{src/modelo/Cliente.java}}: Extende \texttt{Pessoa}, adiciona \texttt{Morada} e serialização. Representa clientes da farmácia.
    \item \textbf{\texttt{src/modelo/Morada.java}}: Value object com rua, cidade e código postal.
    \item \textbf{\texttt{src/modelo/Vendavel.java}}: Interface com \texttt{getNome()} e \texttt{getPreco()}.
    \item \textbf{\texttt{src/modelo/Produto.java}}: Implementa \texttt{Vendavel}; gere ID, preço e stock, com métodos de validação.
    \item \textbf{\texttt{src/modelo/Encomenda.java}}: Relaciona cliente e produtos, controla estados, calcula preço total, oferece construtores sobrecarregados.
    \item \textbf{\texttt{src/modelo/Farmacia.java}}: Núcleo da lógica; gere listas, valida operações, ajusta stock e estados.
    \item \textbf{\texttt{src/persistencia/GestorDados.java}}: Serializa/desserializa dados para \texttt{farmacia.dat}; atualiza contadores de IDs.
    \item \textbf{\texttt{src/gui/FarmaciaGUI.java}}: \texttt{JFrame} com \texttt{JTabbedPane}; trata encerramento com opção de guardar.
    \item \textbf{\texttt{src/gui/PainelGestaoClientes.java}}: Tabela e formulários para CRUD de clientes, com validação de NIF (9 dígitos) e código postal (0000-000), permitindo correção de NIF apenas neste contexto.
    \item \textbf{\texttt{src/gui/PainelGestaoProdutos.java}}: Gestão de produtos com validação de stock/preço e atualização da tabela.
    \item \textbf{\texttt{src/gui/PainelGestaoEncomendas.java}}: Gestão completa de encomendas (seleção de cliente, seleção/pesquisa de produtos, certificação de stock, atualização de estado e sincronização com painel de produtos), apresentando o cliente apenas para consulta durante a edição e com diálogo de gestão que oferece ações de adicionar, remover e guardar alterações.
    \item \textbf{\texttt{src/test/FarmaciaTest.java}}: Testes unitários que asseguram regras de negócio (clientes, encomendas, stock).
    \item \textbf{\texttt{lib/junit-platform-console-standalone-1.10.2.jar}}: Dependência JUnit 5.
    \item \textbf{\texttt{doc/}}: JavaDoc gerado.
\end{itemize}

\section{Funcionalidades Implementadas}

O sistema desenvolvido oferece um conjunto abrangente de funcionalidades organizadas em três áreas principais:

\subsection{Gestão de Clientes}
\begin{itemize}
    \item Interface gráfica com tabela para visualização de todos os clientes registados.
    \item Operações CRUD completas: criação, leitura, atualização e remoção de clientes.
    \item Validação rigorosa de dados: NIF com exatamente 9 dígitos e código postal no formato 0000-000.
    \item Garantia de unicidade do NIF, impedindo registos duplicados.
    \item Possibilidade de correção de NIF durante a edição no painel de gestão de clientes.
\end{itemize}

\subsection{Gestão de Produtos}
\begin{itemize}
    \item Interface tabular para visualização do catálogo de produtos.
    \item CRUD completo com validações de integridade: preço e stock não podem ser negativos.
    \item Gestão de stock com atualização dinâmica da interface após alterações.
    \item Sincronização automática entre painéis quando o stock é alterado através de encomendas.
\end{itemize}

\subsection{Gestão de Encomendas}
\begin{itemize}
    \item Registo de novas encomendas com seleção de cliente (pesquisa por NIF) e produtos (pesquisa por nome ou ID).
    \item Validação em tempo real do stock disponível antes de confirmar a encomenda.
    \item Edição completa de encomendas existentes, incluindo:
    \begin{itemize}
        \item Atualização do estado da encomenda (Em processamento, Pago, Enviado, Entregue).
        \item Diálogo dedicado para gestão de produtos da encomenda (adicionar, remover, ajustar quantidades).
        \item Apresentação do cliente apenas para consulta durante a edição.
    \end{itemize}
    \item Remoção de encomendas com reposição automática do stock dos produtos envolvidos.
    \item Sincronização imediata entre os painéis de encomendas e produtos para refletir alterações de stock.
\end{itemize}

\subsection{Persistência e Validações}
\begin{itemize}
    \item Persistência automática dos dados através de serialização de objetos em \texttt{farmacia.dat}.
    \item Diálogo de confirmação ao encerrar a aplicação, permitindo escolher se deseja guardar os dados.
    \item Carregamento automático dos dados persistidos ao iniciar a aplicação.
    \item Validações abrangentes: NIF único, formato de código postal, stock suficiente, valores não negativos.
\end{itemize}

\subsection{Legenda do Diagrama}
\label{legenda_diagrama}

Para facilitar a compreensão do diagrama de classes apresentado, esta secção descreve os elementos e notações UML utilizadas:

\subsubsection{Organização em Pacotes}
O diagrama organiza as classes em quatro pacotes principais:
\begin{itemize}
    \item \textbf{\texttt{app}}: Contém a classe \texttt{Main}, ponto de entrada da aplicação responsável por inicializar o sistema e carregar dados persistidos.
    \item \textbf{\texttt{modelo}}: Agrupa as entidades de domínio que representam a lógica de negócio: \texttt{Farmacia}, \texttt{Cliente}, \texttt{Produto}, \texttt{Encomenda}, \texttt{Pessoa}, \texttt{Morada}, \texttt{Vendavel} e \texttt{EstadoEncomenda}.
    \item \textbf{\texttt{gui}}: Contém os componentes da interface gráfica: \texttt{FarmaciaGUI} e os painéis de gestão (\texttt{PainelGestaoClientes}, \texttt{PainelGestaoProdutos}, \texttt{PainelGestaoEncomendas}).
    \item \textbf{\texttt{persistencia}}: Inclui a classe \texttt{GestorDados}, responsável pela serialização e desserialização dos dados.
\end{itemize}

\subsubsection{Modificadores de Visibilidade}
Os atributos e métodos são representados com os seguintes símbolos:
\begin{itemize}
    \item \textbf{\texttt{+}}: Visibilidade pública (público) — acessível de qualquer classe.
    \item \textbf{\texttt{-}}: Visibilidade privada (privado) — acessível apenas dentro da própria classe.
    \item \textbf{\texttt{\#}}: Visibilidade protegida (protegido) — acessível na classe e nas suas subclasses.
\end{itemize}

\subsubsection{Tipos de Relacionamentos}

\textbf{Herança (Generalização)}: Representada por uma seta contínua com triângulo vazio apontando para a classe base.
\begin{itemize}
    \item \texttt{Cliente} herda de \texttt{Pessoa} — permite reutilização de código e modelação da relação "é um tipo de".
    \item \texttt{FarmaciaGUI} herda de \texttt{JPanel} — integração com a biblioteca Swing.
\end{itemize}

\textbf{Implementação de Interface}: Representada por uma seta tracejada com triângulo vazio apontando para a interface.
\begin{itemize}
    \item \texttt{Produto} implementa \texttt{Vendavel} — garante que produtos possuem métodos \texttt{getNome()} e \texttt{getPreco()}, permitindo polimorfismo.
\end{itemize}

\textbf{Composição}: Representada por um losango preenchido (diamante sólido) na classe que contém.
\begin{itemize}
    \item \texttt{Cliente} compõe \texttt{Morada} — a morada não existe independentemente do cliente (relação forte, ciclo de vida dependente).
    \item \texttt{Encomenda} compõe \texttt{Produto} — os produtos na encomenda são parte integrante da mesma.
\end{itemize}

\textbf{Agregação}: Representada por um losango vazio na classe que contém.
\begin{itemize}
    \item \texttt{Farmacia} agrega \texttt{Cliente}, \texttt{Produto} e \texttt{Encomenda} — estas entidades podem existir independentemente da farmácia (relação fraca).
\end{itemize}

\textbf{Associação}: Representada por uma linha simples entre classes.
\begin{itemize}
    \item \texttt{Encomenda} associa-se a \texttt{Cliente} — cada encomenda pertence a um cliente.
    \item \texttt{Encomenda} associa-se a \texttt{EstadoEncomenda} — cada encomenda possui um estado.
\end{itemize}

\textbf{Dependência}: Representada por uma seta tracejada com etiqueta descritiva.
\begin{itemize}
    \item \texttt{Main} depende de \texttt{GestorDados} (etiqueta "carrega") — utiliza métodos estáticos para carregar dados.
    \item \texttt{Main} depende de \texttt{JFrame} (etiqueta "cria") — cria a janela principal.
    \item \texttt{FarmaciaGUI} depende dos painéis de gestão (etiqueta "cria") — instancia os componentes da interface.
    \item \texttt{PainelGestaoEncomendas} depende de \texttt{PainelGestaoProdutos} (etiqueta "atualiza") — sincroniza atualizações de stock.
    \item \texttt{GestorDados} depende de \texttt{Farmacia} (etiquetas "usa" e "serializa") — manipula os dados da farmácia para persistência.
\end{itemize}

\subsubsection{Elementos Especiais}

\textbf{Classe Abstrata}: \texttt{Pessoa} é marcada como abstrata (indicada por \texttt{(A)}), não podendo ser instanciada diretamente. Serve como base para \texttt{Cliente} e potenciais futuras subclasses.

\textbf{Interface}: \texttt{Vendavel} define um contrato que \texttt{Produto} deve implementar, permitindo polimorfismo e extensibilidade para futuros tipos de itens vendáveis.

\textbf{Enumeração}: \texttt{EstadoEncomenda} define os estados possíveis de uma encomenda: \texttt{EM\_PROCESSAMENTO}, \texttt{PAGO}, \texttt{ENVIADO} e \texttt{ENTREGUE}, garantindo type-safety e valores fixos.

\textbf{Classe Estática}: \texttt{GestorDados} é marcada como \texttt{<<static>>}, indicando que todos os seus métodos são estáticos e não requerem instanciação.

\subsubsection{Multiplicidades}
As relações incluem multiplicidades que indicam quantidades:
\begin{itemize}
    \item \texttt{0..*}: Zero ou mais (muitos) — \texttt{Farmacia} pode ter zero ou mais clientes, produtos e encomendas.
    \item \texttt{1}: Exatamente um — \texttt{Encomenda} tem exatamente um cliente e um estado.
    \item \texttt{1..*}: Um ou mais — \texttt{Encomenda} contém pelo menos um produto.
\end{itemize}

\subsubsection{Atributos e Métodos Principais}
As classes principais expõem os seguintes elementos:
\begin{itemize}
    \item \texttt{Farmacia}: Mantém listas de clientes, produtos e encomendas; oferece métodos para adicionar/remover entidades e registar encomendas.
    \item \texttt{Encomenda}: Contém identificador único, preço total calculado e estado atual; relaciona-se com cliente e produtos através de um \texttt{Map}.
    \item \texttt{Produto}: Gere stock, preço e identificador; implementa métodos para ajustar stock (\texttt{adicionarStock}, \texttt{removerStock}).
    \item \texttt{Cliente}: Extende \texttt{Pessoa} com nome e NIF; contém uma \texttt{Morada} completa.
    \item Painéis GUI: Cada painel mantém referência à \texttt{Farmacia} e a uma \texttt{JTable} para visualização tabular dos dados.
\end{itemize}

Esta estrutura demonstra a aplicação de princípios fundamentais de POO: encapsulamento, herança, polimorfismo, composição e agregação, resultando numa arquitetura modular e extensível.

\section{Considerações de Implementação}

Durante o desenvolvimento do projeto, foram aplicados diversos princípios e técnicas de Programação Orientada a Objetos, resultando em decisões de implementação que merecem destaque:

\subsection{Encapsulamento e Validações}
O sistema utiliza extensivamente encapsulamento para proteger o estado interno das classes. Todos os atributos são privados e o acesso é controlado através de métodos públicos. Validações rigorosas garantem a consistência dos dados em todas as operações, como a verificação de que o stock nunca assume valores negativos e que os preços são sempre positivos.

\subsection{Validação de Dados de Entrada}
Foram implementadas regras de formato específicas para dados de clientes: o NIF deve conter exatamente 9 dígitos e o código postal deve seguir o padrão 0000-000. A correção do NIF é permitida apenas no contexto do painel de gestão de clientes, mantendo a integridade dos dados em outras partes do sistema.

\subsection{Gestão Automática de Stock}
O sistema implementa uma gestão inteligente do stock, deduzindo automaticamente as quantidades dos produtos quando uma encomenda é registada e repondo o stock quando uma encomenda é removida. Esta funcionalidade garante que o inventário reflete sempre o estado real dos produtos disponíveis.

\subsection{Persistência e Identificadores}
Após o carregamento dos dados persistidos, o sistema atualiza automaticamente os contadores estáticos de identificadores (\texttt{Produto} e \texttt{Encomenda}) para evitar colisões de IDs. Esta abordagem garante que novos registos sempre recebem identificadores únicos, mesmo após múltiplas sessões da aplicação.

\subsection{Sincronização entre Componentes}
Foi implementada uma sincronização eficiente entre os painéis de encomendas e produtos, garantindo que alterações de stock sejam refletidas imediatamente em todas as interfaces relevantes. Esta coordenação melhora significativamente a experiência do utilizador e previne inconsistências visuais.

\section{Conclusão}

O Trabalho Prático 2 alcançou com sucesso todos os objetivos propostos, resultando numa aplicação robusta e bem estruturada. A migração de uma interface de consola para uma interface gráfica baseada em Java Swing demonstrou a aplicação prática dos conceitos de programação orientada a eventos e gestão de componentes gráficos.

A implementação de persistência de dados através de serialização de objetos garantiu que os dados sejam mantidos entre sessões, enquanto os testes unitários com JUnit 5 asseguram a qualidade e consistência da lógica de negócio. A documentação JavaDoc completa facilita a manutenção e compreensão do código.

A organização do código em pacotes bem definidos (\texttt{app}, \texttt{modelo}, \texttt{gui}, \texttt{persistencia}, \texttt{test}) reflete uma arquitetura limpa e escalável, preparada para futuras extensões. A aplicação de princípios avançados de POO, como herança, interfaces, sobrecarga, sobreposição e composição, demonstra um domínio sólido dos conceitos fundamentais da disciplina.

O conhecimento consolidado neste trabalho forma uma base sólida para desafios mais complexos em Programação Orientada a Objetos e desenvolvimento de software em geral. O projeto demonstra a capacidade de transformar requisitos funcionais numa solução técnica completa, bem documentada e testada.
